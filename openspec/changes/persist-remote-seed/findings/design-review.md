# Design review: persist-remote-seed

Reviewed: every Decisions entry in `design.md` against `radicle_impl.cpp`
(`setRemoteSeed`), `settings_store.cpp` (`validate`), the contract comment in
`radicle_impl.h` and the tests in `test_radicle_impl.cpp`; `design.md` and
`proposal.md` against `gh issue view 55` read fresh.

The code takes every recorded decision. Order is shape, probe, store, adopt;
the candidate client is copied and moved in only after the store write; the
stored URL is `candidate.seedUrl()`; `validate` is the single shape rule, called
from both doors. No decision is contradicted or half-applied. The issue's
"Done when" items are all met, and the open question is decided with the
alternatives and their rejections recorded. Nothing the change acted on is
named in the issue and missing from `design.md`. The findings below are gaps
and thin entries only.

- [x] **`dev-writer`** — `radicle_impl.cpp:451` — a choice in the code is not in Decisions: an empty URL is refused, where `SettingsStore::validate("remoteSeed", "")` accepts it and `setSetting("remoteSeed", "")` clears the stored seed.
      A reader could have made `setRemoteSeed("")` mean "reset to default" and delegate to `validate`. The refusal predates the change and the spec states it, but `design.md` records the two doors' differences (shape, network) and not this third one, and it is exactly the case where reusing `validate` alone would silently differ. One sentence under "`SettingsStore::validate` is the one shape rule" would do. Gap, not a contradiction.
      **Fixed** in "Fold the review findings into design.md": a paragraph under "`setRemoteSeed` persists; the UI does not call two entry points" names the empty URL as the doors' third difference, why `setRemoteSeed` refuses it rather than delegating to `validate` or treating it as a reset, and its guard (`an_empty_url_is_refused_and_leaves_the_stored_seed_alone`, the only test the `spec-test-reviewer`'s deletion of the check turned red). The code now also says why beside the check (`radicle_impl.cpp`, in "Refuse a seed that is not a Radicle index, …").

- [x] **`dev-writer`** — `design.md` "Risks / Trade-offs" — the two doors now disagree about the stored form and the entry does not say so.
      `setRemoteSeed` stores and adopts `candidate.seedUrl()` (slash stripped, `radicle_impl.cpp:481`); `setSetting("remoteSeed", "https://x/")` stores `value` verbatim and adopts it via `m_seed.setSeedUrl(value)` (`radicle_impl.cpp:442`). "The stored URL is the one in force" is therefore true of one door only. The Non-Goals cite #65 for `setSetting`'s adoption, but not this divergence, and the trailing-slash `NO SPEC:` test at `test_radicle_impl.cpp:820` is written as though the question were closed. Record it as a known consequence of leaving `setSetting` alone, with where it is tracked.
      **Fixed** in "Fold the review findings into design.md": a Risks entry, "The two doors store the seed in different forms", states the divergence with the `getSettings`/`getCapabilities` disagreement it produces, scopes "The URL is normalised once" to `setRemoteSeed`, and names #65 as the issue that owns `setSetting`'s seed path. #65 does not yet name this divergence; adding it there is a `gh issue` write, which this agent does not make, and is in the hand-back for the runner. The trailing-slash test is no longer `NO SPEC:` (the spec now defines the normalised URL for `setRemoteSeed`), and its comment cites that requirement rather than reading as a general invariant.

- [x] **`dev-writer`** — `design.md:95-104` and `design.md:82-90` — "a store write now also able to fail after a successful probe" is argued, but only one way of failing is tested: the no-path store.
      `a_seed_that_answers_but_cannot_be_stored_is_refused` uses `SettingsStore{""}`. A store with a path whose write fails (unwritable directory, failed rename) goes through the same `isError(stored)` branch, so the code is right, but the entry presents the general case as pinned when only the empty-path instance is. Either say that, or add a test with a real path that fails to write. Suggestion; the code is correct.
      **Fixed** by adding the test: `a_seed_that_answers_but_whose_settings_file_cannot_be_written_is_refused` (in "Refuse a seed that is not a Radicle index, …") gives the store a path whose parent is a regular file, so the directory cannot be made and the file cannot be opened whoever runs it (no reliance on permissions, which a root sandbox would ignore). It passed against the code as it was, as expected for correct code; adopting before the store turned it red alongside the no-path test (measured, see the next box). "A seed that cannot be stored is refused" in `design.md` now names both ways a store fails and both tests.
