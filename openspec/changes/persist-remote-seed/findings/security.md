# Security review: persist-remote-seed

Dimension: security only (correctness, readability and architecture are other instances).

Reviewed: `RadicleImpl::setRemoteSeed` (`radicle/src/radicle_impl.cpp`), `SettingsStore::validate` / `set` (`radicle/src/settings_store.cpp`), the `SeedClient` probe path it drives, and the spec delta. The untrusted input here is the seed's HTTP reply, and the URL a sandboxed view hands across the QtRO boundary.

Clean areas:

- **Validation is not skippable by call path.** `setSetting("remoteSeed", ...)` and `setRemoteSeed` both go through `validate`, and `set()` still calls it, so the store refuses the same shapes whichever door is used. The extraction in `settings_store.cpp` moved the checks without dropping any; the `kKeyRemoteSeed`, `kKeyMode`, `kKeyGitPath` and `kKeyRadSocket` branches are all intact.
- **The candidate-client copy** shares the std::function transport and copies three strings and a bool. A refusal returns before `m_seed` is touched, so the old rollback's state loss is gone. No aliasing or lifetime hazard.
- **No new authority.** The view could already set and persist any `http(s)://` seed through `setSetting`; `setRemoteSeed` now persists the same set after a probe, so the sandbox boundary is no wider. The seed picker offers only `listKnownSeeds`, so credential-bearing URLs are not a path the UI produces.
- **Stored value** is `candidate.seedUrl()` (trailing slashes trimmed), JSON-escaped by nlohmann on write, so a URL containing quotes or control characters cannot corrupt `settings.json`.
- **Not in the diff, noted only.** `SettingsStore::load()` does not re-run `validate` on a stored `remoteSeed`. A hand-edited `file://` value would be adopted at start, and Qt's network stack can fetch `file://`. Anyone who can edit that file already has the user's privileges, so I raise no box for it.

Mutation tool: not run. The change is C++ in `radicle/src`, which the overlay lists as having no mutation tool, and the core unit-test build is a slow Nix build. The probes below were run directly against nlohmann_json 3.11.3 (`tmp/probe.cpp`, not committed).

- [x] **`dev-writer`** — `radicle/src/radicle_impl.cpp:494` — A seed that answers 200 with a non-object JSON body is persisted and adopted, and then `setRemoteSeed` throws instead of returning `{"error":...}`.
      **Scenario:** the user picks a URL whose `/api/v1` returns `[]`, `"x"`, `123` or `null` with HTTP 200. `SeedClient::getJson` returns it as success; `isError` is false because it only treats an *object* with an `error` key as an error. So `setRemoteSeed` passes the probe, `m_settings.set` writes the URL to `settings.json`, `m_seed` is replaced, `remoteSeedChanged` fires, and only then does `index.value("nid", "")` run on a non-object. I confirmed it throws `json.exception.type_error.306 cannot use value() with array/string/number/null`. Neither `radicle_impl.cpp` nor `radicle_ui_backend.cpp` has any `try`/`catch`, so the exception leaves the QtRO slot and ends the host process. The state is committed before the crash, so the next start still holds the seed. This contradicts the contract in `radicle_impl.h` ("Any failure is `{"error":"..."}` and changes nothing"). The throw predates this change, but persisting before it is new, and a refusal path that throws is the one failure this reshape was meant to make impossible. No test feeds a non-object probe reply.
      **Severity:** medium. A crash reachable from a remote server's reply, which the overlay names as untrusted. Fix by requiring the probe reply to be an object (an error otherwise) before storing, and add a regression test with an array reply that asserts nothing is stored.
      **Fixed** in "Refuse a seed that is not a Radicle index, and shape-check the stored URL": `SeedClient::probe` now refuses anything but a JSON object with a string `apiVersion`, as the spec's new "A seed answers its probe only with a Radicle seed index" requires, so a non-object never reaches the store; the reply's `nid` is read from the probe's cached string (`SeedClient::nid()`), not `index.value(...)`. Regression test `a_success_that_is_not_a_seed_index_is_a_failed_probe` (bodies `[]`, `null`, `"ok"`, `42`, `{}`, `{"apiVersion":6}`, `not json`; asserts refusal, kept seed in force and stored, no event) was watched failing first: "Unexpected exception: type_error.306 cannot use value() with array". `a_nid_that_is_absent_or_not_a_string_is_reported_empty` failed first with type_error.302 on `"nid":5`.

- [x] **`dev-writer`** — `radicle/src/seed_client.cpp:117` — An HTTP error body of `{"error": <non-string>}` makes `getJson` throw, and `setRemoteSeed` is a call path that reaches it from the picker.
      **Scenario:** a seed answers non-2xx with body `{"error":5}`. `parsed["error"].get<std::string>()` throws `type_error.302 type must be string, but is number`, with the same lack of any `catch`. It fires inside `candidate.probe()`, before anything is stored, so no state is corrupted, but the host dies where `{"error":"..."}` is promised. Pre-existing and not caused by this diff; I raise it because `setRemoteSeed` is the entry point that sends a user-chosen, therefore attacker-nameable, server URL straight into it.
      **Severity:** low to medium; the same fix pattern (check `is_string()` before `get`) applies to every `getJson` caller. It can be deferred to its own issue, and says so.
      **Fixed**, not deferred, in "Refuse a seed that is not a Radicle index, and shape-check the stored URL": the spec now requires a failure status to be a failed probe whatever its body, `{"error":5}` named. `getJson` surfaces the seed's `error` only when it is a string and otherwise falls back to the status, so every `getJson` caller is covered by the one check. Regression tests, both watched failing first with "type_error.302 type must be string, but is number": `a_failure_status_is_a_failed_probe_whatever_its_body` (through `setRemoteSeed`, status 500 with `{"apiVersion":"6.2.0"}` and `{"error":5}`) and `an_error_status_whose_error_is_not_a_string_still_becomes_an_error_object` (`test_seed_client.cpp`, through `getRepo`). Control `an_error_status_surfaces_the_seeds_own_message` shows a string `error` is still surfaced.

- [x] **`dev-writer`** — `radicle/src/seed_client.cpp:133` — "The seed answered" is any JSON at all, so `setRemoteSeed` stores a server that is not a Radicle seed.
      **Scenario:** `https://example.com` serves JSON at `/api/v1` with 200 (any JSON API will do, including `{}`). `probe()` returns it, `apiVersion` and `nid` stay empty, `setRemoteSeed` replies `{"seed":"https://example.com","apiVersion":"","nid":""}` and persists it. The design, spec and header comment all describe the probe as proving the seed answers; the stored seed is only proven to return JSON. Before this change the same URL was adopted for one session; now it survives every restart, until the user picks another. Persistence turns a mistyped or hostile URL into a standing misconfiguration, and every `remote*` call then returns that server's data in a shape the views render.
      **Severity:** low; the user has to choose the URL. Requiring a string `apiVersion` in the probe reply before storing closes it, and also covers the object case of the first finding's fix. If the owner accepts "any JSON" as the bar, say so in `design.md`.
      **Fixed** in "Refuse a seed that is not a Radicle index, and shape-check the stored URL", by the same `probe` change as the first box: the bar is now a JSON object with a string `apiVersion`, which the spec states. `{}` and `{"apiVersion":6}` are rows of `a_success_that_is_not_a_seed_index_is_a_failed_probe`, which failed first (both were stored and adopted). The reasoning is under "What answering the probe means" in `design.md`.

- [x] **`dev-writer`** — `radicle/src/radicle_impl.cpp:483` — The refusal for a failed store write repeats the store's message, which names the settings file's absolute path, to the view.
      **Scenario:** the seed answers but `settings.json` cannot be written; `SettingsStore::set` returns `could not write settings to /home/<user>/.local/share/radicle-module/settings.json`, and `setRemoteSeed` wraps it into the `{"error":...}` it hands the sandboxed QML view. The overlay names a filesystem path in an error to a caller that should not learn it as a shape to watch. `setSetting` already returns the same string, so this adds no new disclosure of what a view can learn; it adds a second route to it.
      **Severity:** low, a defensible choice and not a defect. Either say "could not be saved" and drop the store's text, or record in `design.md` that the path is acceptable to disclose.
      **Rejected** as a change; recorded in `design.md` under "A seed that cannot be stored is refused", in "Fold the review findings into design.md", as the second of your two options. The path is the module's own settings file under the profile's XDG data directory, neither key material nor the user's Radicle home; `setSetting` already hands the same string to the same view, as you note; the live `module-settings` "A view renders settings from the reply it was given" requires a settings refusal to be shown verbatim and to name the path tried; and "could not be saved" with no path gives a user nothing to go and fix. The one case where the store's text was useless, the empty path, now names its cause instead (`readability.md`'s first box).

## Round 2

Dimension: security only. Reviewed the tree at `35f8d35`, concentrating on `git diff 1973b69 HEAD`: the stricter `SeedClient::probe`, `getJson`'s `error` handling, the two-form shape check in `setRemoteSeed`, the `nid` handling, and the new spec requirements.

Clean areas:

- **The three round 1 throws are closed.** `probe()` rejects a non-object (the `is_object()` test short-circuits before `contains`/`[]`), a missing or non-string `apiVersion`, and `getJson` guards `parsed["error"]` with `is_string()`. I found no other `get<>`/`value()` on a seed-controlled value on the probe path. `parse(..., false)` yields `discarded` for invalid UTF-8 and malformed input, so no exception leaves from there.
- **The two-form shape check holds.** `https://`, `http://`, `https:///`, `/` and `//` all normalise to something `validate` refuses; nothing past the check reaches the store or the client in force. The `{seedUrl, candidate.seedUrl()}` loop binds to the initializer list's own copies, which live for the whole loop.
- **A refusal still changes nothing.** The candidate is the only object `probe()` mutates (it clears `m_apiVersion`/`m_nid` on the copy), and `m_seed` and the store change in one synchronous tail with no yield between them. The nested event loop in `httpGet` can run another call mid-probe, but the outcome is last-completer-wins with the store and the client in force still agreeing.
- **`nid` and `apiVersion`** reach the reply as strings the JSON parser has already validated as UTF-8, and no QML file reads either, so a hostile seed can set them but nothing renders them.
- **`probe()`'s new refusal text** echoes only the URL the caller supplied.
- **Not in the diff, noted only.** A seed's own `error` string reaches `StatusStrip`'s `Text`, which has no `textFormat`, so `AutoText` may read it as rich text. That path (`getJson` to `nav.fail`) predates this change and the diff does not widen it. The probe, redirect (`NoLessSafeRedirectPolicy`) and unbounded-body behaviour of `httpGet` are also unchanged, so a view-chosen URL being a port-probing oracle is the same as before.

Mutation tool: none for the C++ core (overlay). Instead I compiled `seed_client.cpp` against nlohmann_json 3.11.3 with a fake transport (`tmp/probe2.cpp`, not committed) and drove `probe()` with the bodies below.

- [x] **`dev-writer`** — `radicle/src/seed_client.cpp:143` — A 2xx probe body that carries an `error` key is relayed to the view verbatim as the refusal, so the reply is not `{"error":"..."}` and a falsy `error` reads as success.
      **Scenario:** a seed answers 200 with `{"error":null,"apiVersion":"6.2.0"}`. `getJson` returns the parsed body untouched on its `ok` path, and `probe()` returns it at `if (isError(index)) return index;` (`isError` is true for any object with an `error` key, whatever its type or value), so `setRemoteSeed` dumps `{"apiVersion":"6.2.0","error":null}`. Nothing is stored and the seed in force is untouched, so the C++ side is right. But `Radicle.js` `parse` decides failure with `if (doc && doc.error)`, so for `null`, `""`, `0` and `false` it returns `ok: true`, and `Main.qml` `setSeed` takes the success branch: it clears the busy state, calls `nav.reset()` and `repoList.reload()`, and does not snap the picker back, so the picker names a seed whose data is not on screen. That is the silent failure the refusal path in `setSeed` exists to prevent. Measured: the probe harness gave `isError=1` and the raw object back for `{"error":null,…}`, `{"error":""…}`, `{"error":0}`, `{"error":false}`, `{"error":5}` and `{"error":{"k":"v"}}`. The other 2xx rows the new test covers (`[]`, `null`, `"ok"`, `42`, `{}`, `{"apiVersion":6}`, `not json`) never contain an `error` key, so none of them reaches this line.
      This contradicts the new requirement "A seed answers its probe only with a Radicle seed index" (every other outcome MUST be refused as `{"error":"..."}`) and the header contract in `radicle_impl.h`. It also relays the seed's whole body, unbounded and with any extra keys, to the sandboxed view.
      **Severity:** low to medium. The seed is one the user chose, nothing is stored wrongly, and the consequence is a misleading success in the UI plus an off-contract reply, not corruption or a crash. Fix: have `probe()` build its own error for a 2xx body that is an object with an `error` key (the seed's string message when `is_string()`, else the fixed "not a Radicle seed" text), and add a row to `a_success_that_is_not_a_seed_index_is_a_failed_probe` and to the spec's scenario with `{"error":null}` that asserts the reply's `error` is a non-empty string. The same line in `getJson` serves every other caller, which can fix it once there instead.
      **Fixed** in `3ec2b22`, as you proposed: `probe()` builds its own error for a 2xx object with an `error` member — "<url> answered /api/v1 with an error", plus the seed's text only when that is a non-empty string — and never returns the seed's body. It can tell the body is the seed's through a private `SeedClient::fetch` that returns whose body it is, so a seed can no longer forge the discriminator (`architecture.md`'s round-2 second box). The spec now has the scenario with your bodies. Regression test `a_success_carrying_an_error_member_is_a_failed_probe` (`{"apiVersion":"6.2.0","error":"x"}`, `…"error":null`, `…"error":""`, `{"error":false}`, `{"error":5}`) asserts a non-empty string `error`, no other member, the kept seed in force and stored, and no event; it was watched failing first ("expected [1] but got [2]": the relayed body). The failure-status side of the same rule is closed too: `fetch` surfaces a seed's `error` only when it is a non-empty string, so a 500 with `{"error":""}` falls back to the status (`an_error_status_whose_error_is_empty_falls_back_to_the_status`, and a new row of `a_failure_status_is_a_failed_probe_whatever_its_body`, both watched failing first with an empty message). Because that check is in `fetch`, it serves every `remote*` caller. Mutation evidence for both checks is in `design.md`.

- [x] **`dev-writer`** — `radicle/src/radicle_impl.cpp:487` — `setRemoteSeed` now persists a URL with embedded credentials, in a world-readable file and into every later error message; round 1's reason for not raising this does not hold.
      **Scenario:** round 1 noted "the seed picker offers only `listKnownSeeds`, so credential-bearing URLs are not a path the UI produces". `SeedPicker.qml` is `editable: true` and `onAccepted` sends whatever the user types to `seedChosen`, so `https://user:token@seed.example.test` reaches `setRemoteSeed`. The shape rule only checks the scheme prefix, so the URL passes, is probed (Qt turns the userinfo into Basic auth) and is stored whole: `settings.json` is created by `std::ofstream` (mode `0666 & ~umask`, normally `0644`, in a `0755` directory) and `getSettings` hands the secret back to any caller. `Main.qml` `setSeed` also writes it to the status strip as "Cannot use <url>: ...". Before this change a picker-typed seed lived in memory only, so the secret was never written to disk; the persistence is what is new.
      **Severity:** low, and a defensible call either way. Either refuse a URL whose authority has userinfo in `validate` (one more shape rule, shared with `setSetting`), or record in `design.md` that a credential in a seed URL is the user's to place and is stored as typed. No test pins either behaviour today.
      **Fixed** in `3ec2b22`, by the first of your options, which the `spec-writer` adopted in round 2 ("A seed URL carrying credentials is refused"). `SettingsStore::validate` refuses a non-empty `remoteSeed` whose authority (between `://` and the first `/`, `?` or `#`) contains `@`, with a message that names the rule and no part of the URL; `setSetting` therefore refuses it, and `setRemoteSeed` refuses it before any request because it asks `validate` first. Regression tests, both watched failing first (the URL was accepted): `a_seed_url_with_credentials_is_refused_and_its_secret_not_echoed` (through `setSetting`, three URLs including one with a later `@` in the path; the message never contains `s3cr3t` and the stored seed is kept) and `set_remote_seed_sends_no_request_for_a_url_with_credentials` (no request, no echo, seed in force and stored kept, no event). `an_at_after_the_host_is_not_a_credential` is the control, one row per terminator. Disabling the check turns the first two red (measured). The view's "Cannot use <url>" status line and a hand-edited settings file are out of scope, as `proposal.md` says; the reasoning and the alternatives (accept, strip, refuse in `setRemoteSeed` only) are under "A seed URL carrying credentials is refused, by the shape rule" in `design.md`.
