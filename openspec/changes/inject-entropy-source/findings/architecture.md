Review dimension: **architecture** only (correctness, security and readability are other instances).

Reviewed: `radicle/rust-ffi/src/profileinit.rs`, `radicle/rust-ffi/tests/profile_init.rs`, `docs/rust-ffi.md`, `design.md`, the spec delta, and `radicle/src/radicle_ffi.h`, `radicle/rust-ffi/src/lib.rs`, `radicle/rust-ffi/Cargo.toml` and `radicle/flake.nix` for the boundary.

**Clean, and checked against the overlay's "the interface stays narrow":**

- The C ABI is unchanged. `radicle_local_init_profile` still takes three `const char*` (`radicle/src/radicle_ffi.h:258`, `lib.rs:459-465`), and `lib.rs` calls `profileinit::init_profile`, which fixes the opener to `open_system_entropy`. `init_profile_with_entropy` has no `extern "C"` wrapper and no `#[no_mangle]`; it is generic, so it is not even a linkable symbol in the staticlib. No caller across the FFI boundary can reach it, and no JSON field, path or environment variable chooses the source. The seam does not widen what a sandboxed caller can reach.
- The dependency set is unchanged: no `Cargo.toml` or `Cargo.lock` edit, so the vendor hash is not touched.
- Taking an opener rather than an open reader is the right shape and is the least invasive one: it keeps the open at the point it already occupied, after every refusal. The design records this and two tests pin it.
- The production path is `init_profile` -> `init_profile_with_entropy(open_system_entropy)`, a one-line delegation, so there is one body and no second copy of the creation logic to drift.
- The "draw is a separate job" shape is sound: `draw_seed` does one thing (open, fill 32 bytes, name every failure with one prefix), and `read_exact` is std's loop rather than a hand-written second copy.
- Making `init_profile_with_entropy` a `pub` function of the rlib widens the crate's Rust surface (the crate builds `["staticlib", "rlib"]`, `Cargo.toml:11`). Nothing outside this crate links the rlib, and `design.md` Decision 1 weighs `#[cfg(test)]`, a cargo feature and an environment variable and rejects each with a reason. I accept that trade-off and open no box on it.

- [ ] **`dev-writer`** — `design.md:47` and `:90`, `tasks.md:50`, `docs/rust-ffi.md:37` — the "cbindgen does not emit it" argument names a mechanism this tree does not have, and the repo's own docs contradict each other about it
      **Scenario:** `design.md` Decision 1 and task 1.8 say "`init_profile_with_entropy` is not `extern "C"`, so cbindgen emits nothing for it", and `docs/rust-ffi.md:37` says "`radicle_ffi.h` is cbindgen-generated but checked in". The tester's note on task 1.8 and the comment above `the_declared_init_prototype_has_three_const_char_pointer_parameters` say the header is "checked in by hand, not generated by cbindgen". `grep -rn cbindgen` over `*.toml`, `*.nix`, `*.rs`, `*.h` and `*.cpp` finds no `cbindgen.toml`, no `build.rs`, no build-dependency and no workflow step, so nothing generates the header. A reader who later has to decide whether a new Rust function reaches C++ is told two incompatible things. The real guarantee is the one the code states: there is no `extern "C"` wrapper and the header is edited by hand. Without a generator, the reason it cannot appear in the header is that nobody wrote a declaration for it.
      **Severity:** low, documentation of the boundary. It is the load-bearing sentence of the "closed ABI" decision, so it should be true. **Genuine defect** in the record, not a code defect. Fix whichever side is wrong: correct `docs/rust-ffi.md:37` if the header is hand-written, and reword Decision 1 and task 1.8 to say the guarantee is "no `extern "C"` wrapper and no declaration in a hand-maintained header".
