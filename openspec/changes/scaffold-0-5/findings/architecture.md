# Architecture review — scaffold-0-5

Dimension covered: **architecture** only. The diff has no module source
(`radicle/src/`, `rust-ffi`, `radicle-ui/src/`) beyond one comment in
`settings_store.h`, so there was nothing to mutate; every finding is on the
shape of the pin set, the launch environment, the workflow and the prose.

- [ ] **`dev-writer`** — `scaffold.toml:92` (`WAYLAND_DISPLAY = "/run/user/1000/wayland-0"`) vs `CLAUDE.md` "The one exception is a value that belongs to one developer" and `design.md` Decision 4/5 — the change breaks its own rule.
      **Scenario:** CLAUDE.md, written in this same change, says `scaffold.toml` is tracked so "a path into your own home directory does not go there"; Decision 4 rejects `RAD_HOME` in `scaffold.toml` as "the same mistake as the hardcoded `runtime_dir` Decision 5 removes". Decision 5 then commits a hardcoded per-machine session path (`/run/user/1000/...`) to the same file, in the global `[basecamp.env]`, so it reaches every profile and every developer. A developer with another uid gets "Failed to create wl_display" (the control row of the Decision 5 table). One on an X11-only session gets a forced Wayland backend where the old pin launched fine on xcb, which is a regression the design records ("Under the pin, the same session left `WAYLAND_DISPLAY` unset, so Qt chose xcb") and leaves unsolved.
      **Fix:** either reconcile the two rules (CLAUDE.md names this line as the deliberate exception and says why it differs from `RAD_HOME`) or find a form that is not per machine (does v0.5.0 expand `$XDG_RUNTIME_DIR` in `[basecamp.env]`? that is a ten-minute read of its `launch_env`, and the design never records having checked). The rejected-alternatives list does not include it.
      **Severity:** medium, a decision inconsistent with the repo's own recorded principle. Not a defect in any gate.

## Clean, and observations that need no box

- **The interface seam is untouched.** `radicle_impl.h`, the FFI entry points, `guarded()` and every QML component are unchanged; the one `settings_store.h` hunk is a comment whose new text matches what `scaffold.toml` now says.
- **The two-process Basecamp build (Decision 8) is the right shape.** `nix path-info --derivation` followed by `nix build "$drv^*"` is a sound split. The logos substituter and `accept-flake-config` are set globally in `nix.conf` by `install-nix-action`, so the second command does not lose the flake's `nixConfig`; I checked that, since a build without `--accept-flake-config` would otherwise silently drop the substituter. The sampler in the same step is a diagnostic sharing a step with the build; acceptable and recorded, and the `trap` kills the subshell but not its in-flight `sleep`, which costs nothing.
- **Six cold jobs each compile the same Basecamp** (Decision 8 "Accepted for now"). A single build job that saves the store cache, with the spec matrix `needs:` on it, would cost one 24-minute build instead of six, and is the reshape this change makes more valuable than before. It is a larger change than this piece should carry, so it is recorded here rather than boxed.
- **`radicle-ui/flake.nix` carries a tag with no lock file** (pre-existing, Decision 3 explains the lock). It makes the builder-tag agreement lint above more useful, not less.
- **The `source.yaml` scroll step** finds a ListView by `positionViewAtIndex` plus a count equal to the entry count. That is a structural probe by design, throws with a named reason when it misses, and the comment says why an id cannot be used. Fine for a spec; it would not be for module code.
- **Pin copies verified against the design's claims** where this tree allows it: `bbe5da0e…` and `d3af2972…` appear once each in `scaffold.toml`, `LGS_VERSION` is `0.5.0` in both workflows, both builder tags are `0.3.0`, and `git grep` finds no leftover `runtime_dir` that is not an explanatory mention (the `docs/M3-phase0-*` hits are historical findings documents).
